# Sesiones module — conventions and gotchas

- A sesión tracks **two independent lifecycles**, not one: `estado_foto` and `estado_video` on `sesiones`, each nullable (real MySQL `ENUM` columns, not free text). `NULL` means that part doesn't apply to this session — never repurpose it as a third state. There is no `tipo`/`estado` single field; don't reintroduce one.
- Pipeline for each part: `idea → planificacion → edicion → subiendo → completado` (`SesionModel::ESTADOS`, `SesionModel::PARTES = ['foto','video']`). Always change a part's state through `SesionModel::cambiarEstado($id, $parte, $nuevoEstado)` — it writes `sesion_historial_estados` (with `parte` + `estado`) in the same transaction. Never `update()` the column directly. Adding a new value here means a migration to widen the `ENUM` on both `sesiones.estado_foto`/`estado_video` and `sesion_historial_estados.estado` — the PHP `in_list[...]` validation rule alone is not enough, the DB will reject an unlisted value.
- **`idea` is not a separate entity** — it is the pipeline's first stage, with the exact same functionality and data as any other stage (moodboard, situaciones, equipo, model releases, briefing, notas...). There is no `IdeaModel`/`SesionIdeas` controller and no separate `ideas` table anymore (migration `2026-07-28-000001_RestoreIdeaEstadoEnSesiones` folded that back into `sesiones`, reverting an earlier attempt at a separate module that turned out to be the wrong model). A session is created directly at `idea` instead of `planificacion` via a checkbox on the create form (`es_idea` post field in `Sesiones::store()`); moving it forward is just changing its stage via the normal "Cambiar etapa" dropdown, like any other transition — there is no dedicated "promote"/"convert" action.
  - The **only** thing special about `idea`: the sessions list (`sesiones/index.php`) hides it by default (`estadosVisibles()` always excludes `'idea'` from the default filter set) — a dedicated "Ideas" filter chip shows it, combining with the other stage chips using the same OR logic.
- The sessions list (`sesiones/index.php`) is a table, **one row per session** by default (or one row per applicable part when the "Dividir" toggle is on), entirely client-rendered from a `SESIONES`-like JSON blob embedded by the controller — not server-looped HTML. Each part shows as a 5-segment progress bar (`idea/planificacion/edicion/subiendo/completado`), filled up to its current stage; clicking a segment calls `Sesiones::estado` (no page reload). Filtering/sorting/hide-completed/split are all client-side JS state, nothing server-side.
- **Two view sets** since 2026-11-14, chosen by `ses_vista()` (`app/Helpers/sesiones_helper.php`; `?nueva=0|1` stored in the PHP session, new by default — same pattern as Rodajes/Lectura/Gimnasio). Classic: `index.php`/`show.php`/`form.php` (the bullets above/below describe these). New fv style: `index_nueva.php`/`show_nueva.php`/`form_nueva.php` + `_cabecera.php`, `_mb_grupo_nueva.php`, `_mb_item_nueva.php`, `_mensaje_nueva.php`, `public/assets/css/sesiones.css`, `public/assets/js/sesiones.js`. Both hit the same controller endpoints; keep them working with both.
  - `index_nueva.php` is server-rendered (not the JSON blob): one row per session, tabs Activas/Ideas/Completadas/Todas via `ses_grupo()` (idea = all applicable parts at `idea`; completada = all at `completado`; else activa) — ideas stay hidden by default as required. Counters per session come from `Sesiones::resumenTablero()` (grouped queries, incl. linked Rodajes progress).
  - `index_nueva.php` also has a **"Por trabajo"** mode (toggle remembered in localStorage): one card per *part* (foto/vídeo) in columns Preparar (planificacion) / Editar (edicion) / Subir (subiendo) — idea and completado are not pending work. Filter Todo/Solo foto/Solo vídeo. Each part has ONE identity colour defined in `ses_partes()` (foto pink `#f472b6`, vídeo violet `#a78bfa`, picked not to clash with the stage colours of `ses_estados()`), exposed as CSS var `--p` (stage colour is `--c`): full-height band on work cards, part icons in the board rows, ficha and filter. "Time in stage" = `MAX(cambiado_at)` per sesion+parte from `sesion_historial_estados` (fallback `creada_at`; `store()` writes no history). The advance button just calls `Sesiones::estado` with the next stage. Clicking the stage a part is already in must NOT post (it would add a history row and reset the counter) — both views guard against it. Pause is still per session (user decision 2026-11-14: "de momento pausa todo").
  - `show_nueva.php` uses tabs (Brief · Moodboard · Equipo · Modelos · Rodaje — "Plan" was renamed "Brief" 2026-11-23, data-tab `brief`) instead of accordions. Brief has "Hora y ubicaciones": `sesiones.hora_sesion` + the linked rodaje's `rodajes_ubicaciones` (never duplicated; only their new `hora` column is edited from here, POST `ubicaciones/{id}/hora`). Modelos has reusable profiles (`sesion_modelos` + `sesion_modelo_ropa`, linked per session via `sesion_modelos_sesion`, outfits chosen per session in `sesion_ropa_elegida`); card partial `_modelo_nueva.php` is returned as HTML by every modelos endpoint (no JS duplicate). Notas/briefing are saved by fetch POST to `/actualizar` carrying titulo+fecha_sesion+only that field (Sesiones::update only touches fields present). The new `form_nueva.php` deliberately has NO notas/briefing fields (briefing is Quill HTML; editing it in a plain textarea would show raw tags).
  - Moodboard markup exists twice (PHP partial `_mb_item_nueva.php` and JS `htmlItem()`): change both together. Upload supports drag&drop and Ctrl+V paste onto a group. `equipo/copiar` (POST `{desde}`) copies another session's checklist without duplicates.
  - "Qué llevar" (`sesion_equipo`) has two lists via column `tipo` = `equipo` | `props` (migration `2026-11-15-000001_SesionEquipoTipo`, default `equipo`; `SesionEquipoModel::TIPOS`). `equipo/agregar` takes `tipo`; `equipo/{id}/tipo` toggles between lists; `equipo/{id}/editar` (POST `{item}`) renames (pencil button only — no dblclick: the text sits inside the checkbox <label>, so a double click would toggle it); `equipo/copiar` keeps each item's list and dedupes by tipo+text. The classic `show.php` still shows them mixed in one list.
- `notas` (quick notes) and `briefing` (fuller description for the exportable report, meant e.g. for the model) are separate fields, both edited from small independent forms on the show page — each form carries the *other* field as a hidden input so saving one never clobbers the other.
- Uploaded files (moodboard images, model releases) live under `public/uploads/sesiones/{sesion_id}/...`. Always delete the physical file via `borrarArchivoFisico()` before/with the DB row — don't leave orphaned files.
- The situaciones/moodboard export (`Sesiones::exportar`/`exportarSituacion`) is a printable HTML view, not a PDF library — it relies on the browser's print-to-PDF, styled with `@media print`.
